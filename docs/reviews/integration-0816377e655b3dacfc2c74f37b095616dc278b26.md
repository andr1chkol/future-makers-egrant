## P2: preserve original job correlation when recovering submissions

Original location: `backend/app/integrations/service.py:156-194`, particularly
the recovery query at 159-174 and log call at 187-194.
[Exact reviewed source](https://github.com/andr1chkol/future-makers-egrant/blob/0816377e655b3dacfc2c74f37b095616dc278b26/backend/app/integrations/service.py#L156).

After a worker restart/exhausted lease, recovery runs outside the handler's
request/job ContextVars. It loads only SubmissionRecord and logs submissionId,
extractionId and errorCode. The failed job already holds request_id, id and
attempt, but those fields never reach the recovery event. Thus both
`submission.unknown` and `submission.failed` lose the direct request-to-job
correlation required by QUALITY and the integration task.

Reproduction on the original implementation with the added regression tests:

1. Enqueue an apply job under a known request UUID, then reset the caller context.
2. Claim it, expire its one-attempt lease and let run_once mark it exhausted.
3. Run recover_interrupted_submissions outside any request/job context.
4. Capture formatted JSON. The event has the operation IDs and safe code, but
   no requestId/jobId/attempt. Both parameterized cases fail with
   `KeyError: 'requestId'`.

This is an operational correlation defect. It did not demonstrate duplicate
external writes or incorrect exported values. The external adapter is disabled.
